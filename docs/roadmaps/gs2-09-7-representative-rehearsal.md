# GS2-09.7 representative migration rehearsal

The [governing roadmap](https://github.com/FS-GG/.github/blob/15734f4cb71506d76814e054d0e846babf6909aa/docs/github-substrate-v2-roadmap.md#gs2-09--build-migration-archive-and-rollback-tooling) requires migration, interruption at every step, retry, rollback, rerun, and archive verification on isolated repository and Project copies. The current accepted GS2-09.1–GS2-09.6 receipts establish source contracts. They explicitly do not establish live discovery, a live manifest, an effect executor, published history, or executed rollback. GS2-09.9 supplies a callable ordinary v2 journey, not a fleet migration interpreter. These distinctions remain visible in this rehearsal's evidence.

## Execution boundary

The selected subject is a finite, declared set of isolated GitHub repositories and Project snapshots. Its provider identities, repository IDs, Project ID, capabilities, permissions, source heads, source digests, and complete pagination proofs are recorded before mutation. No production fleet subject is an effect target. The actor has only the scoped permissions required for this copy set. A missing entitlement, page, source identity, or prestate is a refusal, never an absent value.

The rehearsal consumes the exact accepted GS2-09.6 receipt and the GS2-09.9 callable handoff, then produces fresh copy-specific GS2-09.1 discovery, GS2-09.2 manifest, GS2-09.3 transforms, GS2-09.4 operation dispositions, GS2-09.5 history, and GS2-09.6 rollback inputs. Historical controlled fixtures are contract evidence; they are not substituted for the fresh provider readings. Every step is bound to one immutable manifest and exact provider prestate. Ambiguous and unsupported transforms need explicit reviewed dispositions before an effect.

The operational interpreter has a closed set of typed effects for native issue fields and types, hierarchy and blocking edges, Project state, body metadata removal, repository settings, receiver pins, scheduling, and archive publication. It uses the already qualified adapters for each surface. No arbitrary REST request or script supplied by a manifest can become an effect. Every effect persists an intent with its target, expected revision, idempotency identity, epoch generation, source and desired digests, and recovery probe before dispatch. After dispatch it rereads the authority and persists a result receipt. An unknown response is pending until authoritative readback distinguishes applied, proven absent, partial, and indeterminate. The protected journal's expected-parent CAS and generation fence remain the concurrency authority.

## Rehearsal sequence

1. Capture two complete quiescent reads and seal the copy-specific manifest, source bytes, operation population, transform decisions, archive inputs, receiver heads, settings prestate, and rollback inputs.
2. Execute the ordered migration once. At each effect, force interruptions before intent, after intent, before dispatch, after dispatch with the response lost, after readback, and before receipt. Restart from durable provider and journal state for every cut. Record the request count and authoritative target readback; a repeated effect on a known-applied target fails.
3. Re-invoke the exact completed operation. It must be a no-op with no new dispatch and the same final authority digest.
4. Verify every archive record and lookup against the frozen source bytes with the separately retained verifier. Rejected historical records retain their typed reason.
5. From the rollback-eligible verified state, execute the five GS2-09.6 restoration domains in reverse order: authority snapshot, schedules, v1 projections, receiver pins, settings. Interrupt and resume each domain from exact chained receipts; reread the restored source state and epoch. No rollback is offered after `OpenV2`.
6. Start a separately identified rehearsal round from the restored copy, bound to a fresh epoch generation and fresh complete reads. Migrate again and compare normalized end state, archive verification, operation dispositions, and receipt counts with the first round. A new round cannot reuse the first round's idempotency identity as authority.

## Acceptance and controls

Q5 binds the copy population, complete source and target reads, exact predecessor receipts, manifest, every transform and operation disposition, native relations and settings readback, archive records and verifier, and the two migration rounds. Q6 binds every interruption cut, persisted-before-effect intent, fresh-process recovery, lost-response reconciliation, settled replay, rollback receipts, and no duplicate effect. Independently authored black-box cases inject a missing terminal page, one newly added source subject, an unexpected Project item, an ambiguous transform without disposition, a changed receiver head, a wrong field type, a missing native edge, an altered manifest, a stale journal generation, an unavailable observer, a partial settings application, a lost response, and an attempted post-`OpenV2` rollback. Each control must show the precise refusal or pending state and zero unauthorized effects.

The retained report records source and final provider IDs/revisions, request and journal identities, exact command and artifact hashes, interruption point, effect count, readback, duration, API budget, refusal and unknown outcomes, cleanup, and limitations. A successful local model or in-memory copy test alone cannot satisfy this unit. The owning PR and protected acceptance receipt may mark GS2-09.7 complete only after the exact isolated provider run and independent controls pass. GS2-09.8 separately proves no omission over the exact manifest and changed-population controls.

## Implementation status

This document defines the execution touch-set and evidence shape. The repository has the source qualification contracts for GS2-09.1–GS2-09.6 and a controlled `MigrationStepExecution` boundary. It has no GitHub migration provider, multi-step driver, or copy-specific provider capture. GS2-09.7 remains unregistered and unaccepted. Future Q5/Q6 commands must require the isolated run rather than accepting controlled fixtures as provider evidence.

## Canonical protocol correspondence and implementation steps

The authored [literate Quint protocol](../../src/FS.GG.Coordination.Protocol/Protocol.md) is the behavioral constraint. `mutationIntentShapeIsValid`, `mutationResultMayFollow`, and the `MutationResultsAreBound` and `UncertainMutationOutcomesStayUnknown` invariants require a closed mutation kind, exact expected revision, stable operation and idempotency identities, and uncertainty that cannot become absence. The GS2-03.10 journal amendment requires expected-parent CAS, a fresh generation fence immediately before dispatch, durable `InFlight` intent, and recovery-only treatment of a restored in-flight effect. `DurablePlansAreOrderedAndResumable` and `DurablePlanCompensationIsBoundaryBound` require ordered receipts and explicit compensation boundaries. Existing `OrdinaryDelivery.advance` covers one source-delivery operation; GS2-09.1–GS2-09.6 provide pure migration facts and plans, with no migration execution function.

The implementation sequence, checked against the unchanged protocol, is:

1. Add a closed migration-step execution boundary in `FS.GG.Coordination.GitHub`. It binds one manifest, source/desired state, mutation kind, expected revision, epoch and journal generation, persists intent before dispatch, and classifies recovery from fresh authority reads. Controlled tests exercise interruption and unknown outcomes. Verify the mutation and durable-plan Quint roots after this step.
2. Compose provider readers and interpreters for the declared GitHub surfaces, using the existing adapters. Add an isolated-copy CLI path, protected journal integration, provider response controls, and an exact readback artifact. Verify the same Quint roots and the independent adapter tests after each surface is connected.
3. Register GS2-09.7 with its exact Q5/Q6 gate command identities only when the commands require a real isolated provider report. Run migration, every interruption cut, rollback, rerun, archive verification, and independent controls, then bind the protected acceptance receipt. A green controlled test alone cannot close the unit.

Current status: research and step 1 complete as source work. `MigrationStepExecution.sealStep` binds a closed effect family, manifest, expected and desired target digests, epoch, journal parent/generation, and explicit admission, operation, optional claim, seal, and registry-head authority. `advance` persists intent, promotes it to in-flight before dispatch, refreshes the bound epoch, authority fence, target and journal immediately before the external effect, settles from effect and target readback, and refuses blind replay of a restored in-flight operation. Its journal stages require their exact chained generations, and an observed effect cannot settle directly from `IntentPersisted` without an `InFlight` grant. Controlled tests cover intent, dispatch, lost response, settled replay, unknown/partial outcomes, stale epoch, changed target, altered plan, forged stage generation, external application before grant, and authority drift before and after journal promotion. The full pinned canonical Quint qualification passed against the unchanged authored source (receipt under ignored `artifacts/canonical-quint/`). No spec change is proposed. A failed Quint invariant stops the implementation for diagnosis; it is never repaired by weakening the authored protocol.

Step 2 has a read-only provider slice: `MigrationGitHubRead` pins repository identity, walks the complete REST issue pagination while separately counting pull requests, and walks GraphQL issue-type pagination. It rejects malformed items, duplicate IDs, escaped continuations, absent pages, and any GraphQL `errors` field even when `data` is present. `HttpMigrationGitHubReadTransport` refuses REST non-GET and GraphQL mutation-shaped requests before network dispatch. The two-pass `eng/probe-migration-github-read.fsx` diagnostic ran against the existing private `FS.GG.GitHub.Substrate.Sandbox` repository (provider ID `1353050537`): one REST page contained 2 issues and 18 pull requests, one GraphQL page contained 4 issue types, and the two normalized passes matched at SHA-256 `2fbc66f9e1ac058f87a9a1b02fc955288284c574e592191016eff7e7f2ff2658`. The live organization Projects list also returned partial data with a `FORBIDDEN` error for one Project; this is exactly why partial GraphQL data is rejected. These are diagnostic reads, not an isolated Project copy, full nine-authority discovery, or Q5/Q6 acceptance. Step 2's remaining surfaces, protected journal integration, write interpreter, and exact copy-specific report are pending; GS2-09.7 remains unregistered and unaccepted.
