# Ordinary assignment source kernel

This source candidate implements Delivery [#1038](https://github.com/FS-GG/FS.GG.Coordination/issues/1038) under [LEARN #4647](https://github.com/FS-GG/.github/issues/4647) and the accepted [OR-first design](https://github.com/FS-GG/.github/blob/main/docs/coordination/2026-08-31-operations-research-first-agent-orchestration-design.md), especially sections 4.5–4.7, 5.2, 7.6 and 8.2. It adds pure contracts and decision checks. Existing production composition, experiment gates, protocol decoders, journals, runners and provider implementations continue to own their present behavior.

## Source contract

`OrdinaryAssignment` retains immutable workspace repositories/components and source provenance, a frozen assessment, requested/resolved/observed profile configuration, work identity, attempt/generation, mandatory context/skills/tools/effects, checks, outputs/reviews, resource demand and the original recovery/deadline budget. Ordinary assignment has an optional experiment reference. Neither an assignment nor its digest grants execution authority. A local work identity remains local; it is never converted into a fabricated board issue.

Caller-supplied source-bound completeness evidence is the trust boundary. The independently supplied `AuthoritativeObligations` names its expected work population and binds its complete requirements and source manifest. This cannot discover requirements that its authoritative producer omitted from both the manifest and expected population. Missing completeness, a changed manifest without a new digest, or disagreement between authority and snapshot refuses verification.

The versioned policy is `ordinary-assignment-rules/1`. It filters hard constraints, orders authorized priority descending and original deadline ascending, then compares declared currency micro-units, duration milliseconds and rework milliseconds where the comparison has complete comparable economics. Otherwise the entire comparison uses a declared stable-identity fallback; unknown economics is never zero. Work/profile identity breaks ties. Time is supplied input. This is a bounded policy candidate, with no claim of optimal scheduling, learned effectiveness or economic savings.

Resources use nonnegative signed 64-bit named units: CPU millicores, memory/storage bytes, I/O bytes per second, integer task slots and named quota counts. Addition checks overflow. Unknown hard demand/capacity or incomplete held-reservation population cannot establish a positive proof. The supplied reservation population must correspond to the existing `ProjectState.Reservations`; all held entries count regardless of their terminal description. Process completion is not release evidence. Existing `ProjectOrchestrator`/`SchedulerReservation` provide slot counting and reserved recovery capacity; the new functions do not allocate, release, invoke reducers or implement another scheduler.

Bounds are 32 works, 8 profiles (256 alternatives), 8 repositories, 16 components, 128 obligations per work, 256 dependencies, 64 held reservations, 8 selected candidates, 512 UTF-8 bytes per text field, 2 MiB canonical input and 512 KiB result. Canonical traversal and decision loops have an explicit deterministic evaluation ceiling of 1,000,000. Limit exhaustion is incomplete evidence, never a partly checked success. Record fields/union cases and length-prefixed typed values form canonical identity; work/profile/reservation populations normalize order. Source lists and command/component order remain contract data. Relevant authority, attempt, version or path changes change identity or refuse.

## Independent verification

The verifier accepts authoritative obligations/completeness separately from the planner snapshot and decision. It compares full reconstructed requirements, not just planner-supplied IDs; checks dependencies in selected order, capabilities with observed fixture evidence, tools/context/skills, effects, source-bound checks, original deadlines/recovery, outputs/reviews, profiles/configuration and assignment bindings; then independently sums per-candidate and aggregate resource demand including recovery headroom and all retained reservations. It also checks pairwise writable path conflicts, recovery slots, duplicate/replayed reservations and declared preference totals. It never calls the selector or shares its feasible-set construction. Shared primitives are domain validation, canonical encoding, units and path comparison.

Focused tests require two useful ordinary selections without experiment enrollment: the maintained F# Coordination framework and the maintained Python backend/JavaScript frontend product. Fixture manifests pin revision `9d99573628ee31e966a61a28b9b36f7414b10f33` and literal SHA256/source paths in the test file. Framework commands come from `eng/bootstrap-gates/compiler-and-tests.sh`; product commands and result identifiers come from `PortableWorkspaceExecutorTests.fs`, together with backend/frontend build/test sources and both journey sources. The product journey starts/retires a Python child and invokes Node over loopback HTTP. Its profile requires Python, Node, subprocess launch/retirement and loopback HTTP. These are explicit fixture observations, not installed host claims. Pure tests read/hash/model the closure and never run those journey processes.

Both candidates consume the same frozen capacity, held unknown reservation and recovery headroom. Tests reject overcommitted or overlapping unions even where either candidate alone fits. Mutation controls separately remove dependencies, checks, capabilities, generation, recovery and deadlines from snapshots and candidates; alter or omit authoritative input; test replay, ordering, unknown resources/holds, exhausted budgets, forbidden effects, invalid outputs and missing observed capabilities. Constructed multi-repository/local cases demonstrate data preservation and unsupported projection, not installed journeys.

## Main field correspondence and refusal matrix

`OrdinaryAssignmentProjection.report` is compiled against the actual `MainAdmissionPreparationRequest`. Its result is a distinct informational record: matched fields, mismatches, residual obligations and informational completeness. It cannot be consumed as Main admission, `LaunchIntent` or a dispatch capability. A positive board-bound, single-repository fixture has all supported fields matched and a nonempty residual list. Every matched field has an independent mutation control.

## Migration and acceptance limits

Owners remain Coordination for controller/runner/journal, SDD for workspace identity, Governance for capability/evidence semantics, Templates for provider payloads/skills, .github for shared policy/clients/registry and Home for actual installed execution. ### Ordinary assignment durable join: source checkpoint

The opt-in Main preparer accepts `--ordinary-assignment-file`. Its closed artifact carries the complete authoritative obligations, frozen snapshot and decision as schema-bound evidence, plus a launch projection. Host re-runs the independent verifier, checks the selected semantic digest and matches actual work identity, principal, generation, reservation, requested configuration, input bytes and the original fixed budget. The second content object is staged before immutable route binding. Route /4 and command /6 envelopes retain separate assignment and object digests while preserving historical inner formats and optional causal metadata. The existing content framing transfers bounded chunks without placing evidence inside control records. Resolver recovery reads and verifies the original object again; runner checks the retained object before workspace materialization and includes its reference in durable launch equality.

This source candidate remains unaccepted until qualification and independent review complete. The early Host build compiled Protocol/Core/storage dependencies and reported one missing Program qualification; that source repair is retained separately from the original failure. Maintained fixtures now cover complete evidence roundtrip, authoritative omission, closed envelopes, request-field mutations, runner prelaunch refusal and controlled invocation/replacement, plus actual PostgreSQL interrupted preparation prefixes and replay. Fixture presence is not an execution result. Local focused tests and the existing Docker-backed PostgreSQL hosted gate must establish actual results; no local PostgreSQL installation or container launch is selected.

Unknown economics remain unknown and experiment enrollment is not required. The retained `Specification.Resolved` and `Specification.Observed` values are historical/input evidence, not observed configuration of the provider selected by this invocation. Actual provider readiness, resolved configuration and lifecycle observations remain owned by the existing provider path. Host joins the requested model/effort/runtime and the actual single-repository baseline, rendered input, identity and original budget. It retains the full provenance source list and independently checks its schema/completeness/semantic consistency; it does not fetch every referenced source or authenticate arbitrary provenance claims. Those labels alone establish no runtime capability or reservation. The ordinary authority producer remains responsible for genuine evidence supply.

Terminal replacement recovery joins the exact persisted launch bytes to a bounded, versioned provider-session receipt and a verified candidate artifact. The receipt retains the observed session and the inspector's original command identity independently of the current recovery command. Its checksum, canonical encoding and origin binding reject missing, corrupt or substituted recovery state. Duplicate launch and reconciliation return the original terminal session without invoking the provider again; cancellation reports that the session is already terminal. A persisted spawn intent without this terminal proof remains unknown and requires reconciliation. Historical records without the new receipt retain their prior interpretation.

Plain Main preparation retains its historical canonical bytes; ordinary and causal wrappers retain their independently validated route bytes. Focused Host and Runner tests cover that compatibility, terminal replay and session identity, missing or corrupt receipts, changed artifact origin, missing terminal artifacts and one invocation. These focused results and PostgreSQL Release compilation do not replace the full hosted PostgreSQL fixture or required exact-head qualification.
