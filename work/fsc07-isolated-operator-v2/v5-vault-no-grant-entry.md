# Proposed v5 vault entry: no-grant refusal

Status: source-only proposed entry, stacked on [#759](https://github.com/FS-GG/FS.GG.Coordination/pull/759). The [entry](../../eng/callable_isolated_v2_v5_vault_no_grant_entry.py) is outside the current installed archive and is not wired to either disabled effect workflow. It names a future protected `read_token_for_public_handle` port but supplies no implementation or route to call it. Both absent and untrusted grant inputs return a frozen exit-78 refusal before inspecting the public identity, request specification, grant bytes or any port. The standalone `execute-native-pull` command also exits 78; extra arguments cannot introduce a grant.

The [controls](../../eng/tests/callable-isolated-v2-v5-vault-no-grant-entry/test_v5_vault_no_grant_entry.py) first failed because this proposed entry was absent. They exercise direct and alternate invocation, untrusted grant bytes and denying ports, a clean-directory `python3 -I -S` run with a token sentinel, unchangeable authority fields, exclusion from the current archive and both disabled workflow gates. They assert zero local token environment, file, socket and SQLite access. These are local source controls, not a protected clean-install proof.

The [#759 public-handle witness](token-custody-identity.md) still does not prove its handle-to-token mapping. A future protected owner must select a vault/backend and independently attest that the opaque public handle and public credential ID map to the exact selected App token without exposing token bytes in evidence. That owner must also review a new runnable source and archive/manifest, install it under an immutable runner, prove the no-grant refusal with independent counters, and separately admit a one-use grant and durable CAS before any token read or provider send. This draft does none of those steps.
