# GS2-09.7 protected run-binding source contract

Status: source-only verifier scaffold, **not installed on a live route**. The reviewed Coordination #552 candidate checks a sanitized `mint-grants.json` and matching token but cannot authenticate that pair's protected run, candidate commit, or nonce. The `.github` #3690 workflow emits no signed envelope or pinned signer key. A digest joining its `preflight.json` and `mint-grants.json` would remain forgeable by a candidate that receives both files.

`eng/sandbox_run_binding_contract.py` defines a detached RSA-PSS/SHA-256 envelope over canonical, domain-separated JSON. It binds the protected workflow repository/path/revision and environment; run ID and attempt; exact candidate SHA and derived nonce; sandbox repository numeric/node ID and Project node ID; exact raw mint-proof SHA-256, token SHA-256, and expiry. The verifier requires a separately pinned SPKI SHA-256 trust anchor and rejects duplicate/unknown fields, malformed claims, unsigned or invalid signatures, stale or changed run facts, proof/token changes, foreign targets, and expired claims. Tests use disposable keys and fake tokens only. The module does not read secrets, call GitHub, or authorize a candidate by itself.

## Protected installation required

1. Admit the `.github` source route separately; #3690's merge remains an unadmitted source-delivery observation. Select and review one exact workflow revision and Coordination candidate. The existing Q4 workflow is not a migration command.
2. On the protected host, after its App mint **and native actor/repository/Project preflight**, produce the envelope from `github.run_id`, `github.run_attempt`, `github.sha`, the reviewed candidate SHA, the exact derived nonce, registered target IDs, the raw proof bytes, token hash, and proof expiry. The signer must be held only by the protected host. The existing App RSA private key could sign this domain-separated envelope if its use is explicitly admitted; otherwise install a distinct protected signing key. Do not pass that private key to the Coordination checkout.
3. Pin the matching public-key SPKI SHA-256 in reviewed candidate source and retain the public key bytes. A candidate-supplied key or fingerprint is not a trust anchor. Key rotation requires a new reviewed candidate and host source. Retain the envelope and public-key fingerprint, never the private key or token.
4. At the protected host, verify the exact envelope fields and signature, proof/token digest, mint and preflight readback, selected repository and Project, current expiry, and candidate checkout before releasing the token to a candidate step. Add independently authored wrong-run, wrong-candidate, wrong-nonce, altered-proof, foreign-key, and missing-signature controls that assert **zero candidate provider calls**. The candidate verifier must also run before either live execute or cleanup route; missing binding refuses. Cleanup still needs a bounded recovery path if signature material is unavailable after an effect.
5. Keep Q5/Q6 native readback separate: nine complete authority passes, copy-specific manifest and operations, all interruption/recovery cuts, archive and rollback evidence, independent controls, cleanup and revocation. A valid binding envelope establishes neither migration correctness nor GS2-09.7 acceptance.

This branch cannot install steps 1–4: the actual signing private key, public trust-anchor fingerprint, protected workflow amendment, admitted host decision, and installed migration interpreter are absent here. The verifier's `expected` argument must eventually come from protected runner facts, not a candidate-writable JSON file or an envelope echo. Even a correctly signed envelope cannot force arbitrary candidate code to invoke a verifier after receiving the token; protected candidate review and a host-side release gate remain necessary. No sandbox dispatch, provider write, receipt, merge, or cutover follows from this source scaffold.
